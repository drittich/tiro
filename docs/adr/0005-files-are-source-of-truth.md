# Per-meeting files are the source of truth; SQLite is a rebuildable index

Each Meeting is a folder at `~/.local/share/tiro/meetings/<date>-<slug>/` (for example `2026-10-17-1405-manual`, with `-2`, `-3`… added on a clash). It holds `meeting.json` (title, app, start and end times, status, whether the user has renamed it (a Summary's title replaces the default title, or an earlier Summary's, but never one the user gave; a file without the field counts as renamed unless its title is still the default), and the Meeting's `tags`: missing until it has been tagged, an empty list when it was tagged and nothing fit, and cleared when a new Summary replaces the one they came from), `transcript.jsonl` (one Segment per line: track, start, end, text, optional speaker), `notes.md`, `summary.md`, the Passages' embeddings (`embeddings.json` and `embeddings.bin`, below), a `screenshots/` directory when Meeting screenshots are on, and a temporary `chunks/` directory. SQLite holds only an index (title, times, status, Tags, and the Passages Search matches) and can be rebuilt by scanning the folders' `meeting.json` files, so it is never migrated or backed up: an index without a column the app now needs is dropped and rebuilt. The Tag vocabulary is collected from every Meeting's `tags` and has no file of its own. When the tagging rules change enough that every Meeting should be tagged again, an empty `.tags-v<N>` marker in the data folder records that every Meeting's `tags` were cleared for rules version N, so the startup backfill re-tags them once. Exported Markdown is rendered from these files on demand and is not stored. Chunk audio is deleted after a successful transcription unless "keep recordings" is on. Recording never depends on the network: failed Chunks stay on disk and are retried with backoff. Each Chunk file is named for its Track, index and span in milliseconds (`others-00007-000152250-000181500.ogg`), so a Chunk left behind by a failure or a restart can still be placed on the timeline when "Retry failed Chunks" merges it into the Transcript. Screenshots are named the same way, by index and Meeting time in milliseconds (`00007-000152250.webp`), so the file name is their whole record: there is no sidecar and no `meeting.json` field. The one exception is an empty `screenshots/.thinned` marker, which says the folder's Screenshots were kept by the current keep rule, so the one-off thinning of older Meetings (ticket 26) skips it.

## Passages for Search are part of the index

Search (ticket 35) matches Passages, not whole Meetings: a Meeting's title, its Summary's sections (split at headings), its Notes' paragraphs (split at blank lines) and windows of about 30–60 seconds of its Transcript (whole Segments, as shown, without fillers). They are stored only in the SQLite index, in an FTS5 table `passages` (the bundled SQLite has FTS5 compiled in), ranked by BM25. Each row has the Passage's text and where it is in its Meeting (source, then a Summary section, a Notes line or a Transcript start time in ms), so a result can open the Meeting there. Like the rest of the index they are never migrated or backed up and are rebuilt from the folders for free.

A second table, `passage_stamps`, keeps for each Meeting a fingerprint of the files its Passages were split from (the size and modification time of `meeting.json`, `summary.md`, `notes.md` and `transcript.jsonl`, plus a splitter version). At startup the Meetings whose Passages are missing or whose files have changed since are indexed again in the background, oldest first. While the app runs, a Meeting is indexed when its Transcript is final (its status becomes complete or incomplete), when it gets a new Summary and when it is renamed. Notes are indexed again only once editing stops (the editor loses focus, closes, or goes 30 seconds without a save), not on every autosave. Deleting a Meeting deletes its Passages, and rebuilding the index drops those of Meetings that are gone. Both tables are dropped and refilled when their shape changes: a `passages_version` row records the FTS5 table's version, and the fingerprint's splitter version makes every Meeting split again when the splitter changes.

## Embeddings are kept in the Meeting folder

Search by meaning (ticket 36) compares the query's embedding with every Passage's. Unlike the Passages, embeddings cost money to make, so they are not kept only in the index: each Meeting folder holds `embeddings.bin`, the vectors as little-endian `f32`s one after another, and `embeddings.json`, its manifest: `model` (the Embedding model's OpenRouter id), `dimensions`, and `hashes`, the SHA-256 (hex) of the text each vector was made from, in the order of the file. The text embedded for a Passage is its text, after its heading for a Summary section. The vectors are stored scaled to length 1. `embeddings.bin` is written before its manifest, each atomically, and a pair whose sizes don't agree is ignored, which only costs embedding that Meeting again.

When a Meeting's Passages are indexed, the ones whose (text hash, model) has a stored vector reuse it, only the others are sent to OpenRouter, in as few requests as fit (at most 96 texts and about 60,000 characters each), and the files are rewritten with the vectors of the Passages the Meeting has now, dropping stale ones. A folder holds one model's vectors, so a new Embedding model embeds every Meeting again, in the background, oldest first. Rebuilding the index re-reads the files and sends nothing for an unchanged Passage. At startup every stopped Meeting's vectors are read into memory, where a query's vector is compared with all of them by brute force: a few hundred Meetings of about 100 Passages, 1536 dimensions each for the default model, is a few hundred MB at most and needs no vector database. A Passage less similar to the query than 0.25 (tuned for `openai/text-embedding-3-small`) is no match, and at most 50 are taken; their ranking is merged with the keyword ranking by Reciprocal Rank Fusion (k = 60) before results are grouped by Meeting. Query vectors are cached in memory only. Deleting a Meeting deletes its embeddings with its folder.

## The spend ledger outlives its Meetings

The Spend of every OpenRouter request (Chunk transcription, Summary, Tags, embeddings) is appended to `~/.local/share/tiro/spend.jsonl`, the spend ledger: one JSON object per line with `at` (UTC), `meeting_id` (the Meeting's folder id, absent for a request made for no Meeting), `kind` (`transcription`, `summary`, `tags`, `embedding` for a Meeting's Passages or a search query, `answer` for an answer to a question asked of the Meetings (Ask), always for no Meeting, with room for later kinds), `model`, `cost` in USD, and, when reported, `prompt_tokens`, `completion_tokens`, `seconds` of audio and `generation_id`. The cost is the `usage.cost` OpenRouter returns with each answer, or failing that, for a successful answer, the one `GET /generation` gives for the answer's generation id. `/chat/completions`, `/audio/transcriptions` and `/embeddings` all return `usage.cost` unasked (checked against the live API in October 2026), so the lookup is only a fallback. Tiro doesn't estimate costs yet: a successful answer whose cost neither gives is logged and not recorded. `estimated: true` is reserved for a cost Tiro works out itself, should that ever be needed. A request that got no answer, or an answer without a cost (such as a rejected `verbose_json`), is not recorded. One that reported a cost is recorded even when Tiro treated it as a failure, such as an empty Summary.

The ledger is the one file outside the Meeting folders that is a source of truth rather than an index. It can't live in the Meeting folders, because deleting a Meeting removes its folder, while the money it cost was still spent. Tiro only ever appends to it and never rewrites, truncates or prunes it, and deleting a Meeting leaves its lines in place. A Meeting's Spend, each month's total (calendar months in local time) and the total to date are derived from it on demand. Nothing is cached in `meeting.json` or SQLite. A line that doesn't parse, such as one cut short by a crash, is skipped. Spend from before the ledger existed is unknown and is not estimated.
